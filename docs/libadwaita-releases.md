# Moving to a new libadwaita

AvaAdwaita runs whatever `gtk.css` the installed libadwaita ships, as long
as it parses cleanly. A new release can still need work: new CSS, renamed
nodes, or new style classes. This is the checklist.

1. **Bump the submodules.**
   ```sh
   git -C external/libadwaita fetch --depth 1 origin tag 1.11.0
   git -C external/libadwaita checkout 1.11.0
   ```
   Bump `external/gtk` to the GTK release libadwaita requires.

2. **Rebuild the bundled stylesheet.**
   ```sh
   tools/build-stylesheet.sh
   ```
   Rename `Sources/Bundled/gtk-<old>.css` to the new version, update
   `StyleSheetLoader.BundledVersion`, `AvaAdwaitaLibadwaitaVersion` in
   `Directory.Build.props`, the embedded resource name, and copy
   any new assets. `tools/build-stylesheet.sh --check` must pass on a
   machine with the new `libadwaita-1.so` installed.

3. **Run the coverage test.** `CoverageTests` parses the new sheet and
   fails on any property, function, selector or at-rule the engine does
   not support. Add each one: the property to
   `tools/adw-css-props/properties.yaml` (then run
   `dotnet run tools/adw-css-props/adw-css-props.cs`), a parser and
   computed value, and a conformance test. `docs/css-support.md` is
   regenerated by the same tool.

4. **Port changed C.** Diff `src/adw-accent-color.c`,
   `src/adw-style-manager.c` (the providers), `src/adw-easing.c`,
   `src/adw-spring-animation.c` and `src/adw-settings-impl-*.c` between the
   tags and port what changed.

5. **Diff the widgets' node trees.** New or renamed nodes break matching
   silently: the sheet parses, but rules stop applying. Regenerate the
   parity data:
   ```sh
   tools/regenerate-data.sh
   ```
   and review the diff of `tests/Data/parity/expected-gtk.json` and the
   goldens. Update the ControlThemes whose trees changed.

6. **Look for new style classes** in the release notes and add them to the
   gallery pages.

7. **Update** `NOTICE.md`, the README and the `oracle` CI image versions.

## Package versions

A package version is the pinned libadwaita version plus a fourth number,
for example `1.10.0.152`. The pin is `AvaAdwaitaLibadwaitaVersion` in
`Directory.Build.props`. A repository test keeps it, the version in
`external/libadwaita/meson.build` and `StyleSheetLoader.BundledVersion`
the same.

The CI pack job sets the fourth number to the CI run number
(`AvaAdwaitaRevision`). Each CI build has a higher version than the build
before it, and a new libadwaita version also gives a higher version. A
re-run of the same CI run keeps its number. Local builds use 0, which NuGet
drops, so they are `1.10.0`. The AppImage uses the same version.
